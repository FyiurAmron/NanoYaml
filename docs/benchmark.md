# Benchmark

A round-trip comparison of NanoYaml, StrictYAML and YamlDotNet on random
data in the strict NanoYaml subset: every file is parsed and written back.

While not exhaustive and done only on a single machine, it can be easily
verified that both the algorithm choice and implementation are indeed faster
than the other competing references.

## Method

- The corpora are generated by `_tools/bench` from fixed seeds, so every
  run sees the same bytes.
- Each parser gets a fixed time budget and is measured on how much it
  gets through: documents per second and megabytes per second.
- The files are read into memory before the clock starts, so the timing
  covers parsing and serializing only, never the disk.
- The .NET runners do a full warmup pass first, so the tiered JIT is
  settled before the measured window. They also report the bytes allocated
  per document on the measuring thread.
- The cold start is measured apart: a fresh process times its very first
  parse and serialization of one file, JIT and type analysis included.
  `run.sh` takes five samples per parser and reports the median.
- The corpus is written with NanoYaml's own serializer, minus the profile
  preamble, so every file is a NanoYaml-subset document by construction.
- In case1 and case2 the parsed document is a generic tree for every
  parser: scalars stay strings, mappings stay mappings, sequences stay
  sequences.
- In case3 and case4 every .NET parser deserializes into the same typed
  object model (`_tools/bench/Models.cs`): classes with string, enum,
  integer, floating-point, decimal, boolean and nullable properties, lists,
  dictionaries and nested objects, plus positional records (`Position`,
  `Effect`) in single fields, nullable fields and lists, and several enums
  per object. Generation checks that each file survives a typed NanoYaml
  round trip byte for byte.
- libyaml is the C reference: release 0.2.5, downloaded and checksum
  verified by `_tools/bench/build-libyaml.sh` and compiled at `-O2` into the
  runner `_tools/bench/libyaml_bench.c`. It loads every corpus, case3 and
  case4 included, into its own node tree (`yaml_document_t`), and writes
  that tree back through its event emitter into a reused memory buffer.
  MB/s counts the same UTF-16 code units as the .NET runners.

## The corpora

| corpus | seed | files | total size | per file | shape |
|---|---|---|---|---|---|
| case1 | 20261022 | 1000 | 1.64 MB | 71 B - 2.8 KB | small documents, 3 to 8 root keys, depth up to 8 |
| case2 | 20261023 | 10 | 3.74 MB | 273 KB - 599 KB | the same shapes, large |
| case3 | 20261024 | 1000 | 2.58 MB | 572 B - 5.4 KB | small typed documents |
| case4 | 20261025 | 10 | 3.58 MB | 145 KB - 564 KB | typed documents, large |
| case5 | 20261026 | 1000 | 2.22 MB | 329 B - 3.8 KB | case1 shapes in flow style where small, about 38% of lines |
| case6 | 20261027 | 100 | 3.39 MB | 26 KB - 43 KB | typed, numbers only: doubles, floats, decimals, ints and longs |

The data mixes plain words, numbers, booleans, nulls, empty strings,
punctuation that needs quoting, non-ASCII text, and long sentences. Keys
are unique within a document. StrictYAML has no typed model, so it runs on
case1 and case2 only; libyaml has none either, so its case3 and case4
numbers are untyped. NanoYaml writes case5 back in the same flow style;
the other parsers pick their own.

The slight edge that SharpYaml has in one case is precisely due to the overhead
needed to be able to handle bigger data sets more efficiently by NanoYaml.
Even then, it's negligible in all practical situations.

## Round-trip fidelity

| input | NanoYaml | YamlDotNet | StrictYAML |
|---|---|---|---|
| `num: "42"` | `num: "42"` | `num: 42` | `num: 42` |
| `flag: "true"` | `flag: "true"` | `flag: true` | `flag: true` |
| `empty: ""` | `empty: ""` | `empty: ''` | `empty:` |
| `tilde: "~"` | `tilde: "~"` | `tilde: ~` | `tilde: ~` |

## Running it

```sh
bash _tools/bench/run.sh
```

The results land in `artifacts/bench-results` as JSON, and the table above
comes from `_tools/bench/report.py`. The StrictYAML runner needs Python
with `strictyaml` installed; the libyaml runner needs `curl` and a C
compiler; the .NET runners need only the .NET SDK.
